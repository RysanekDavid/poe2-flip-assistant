# PoE2 data-source strategy

Research date: **2026-08-06**

## Decision

Do not crawl and mirror the whole PoE2DB website.

Use a layered data pipeline instead:

1. **RePoE** for versioned static game data.
2. **GGG Currency Exchange API** for authoritative hourly exchange history.
3. Existing **Path of Exile trade2** integration only for bounded, on-demand listings and
   comparables while its unsupported website-API status is reviewed.
4. **poe2scout / poe.ninja** only where the first three layers do not provide an equivalent
   aggregate.
5. **PoE2DB** only for small, reviewed tables that are missing from RePoE.

This gives us stable local snapshots without coupling the application to PoE2DB's HTML layout.

## What the PoEDB Developer API page actually is

[PoEDB Developer API](https://poedb.tw/us/Developer_API) is a directory of Path of Exile
developer resources. It is not an API for downloading PoEDB's own item/modifier database.

The page distinguishes between:

- website endpoints authenticated with `POESESSID`, which it says are not officially supported;
- officially supported OAuth endpoints, which expose fewer functions.

Its linked [Swagger page](https://poedb.tw/us/poe-api) describes itself as a sample Path of Exile
API and points clients back to GGG's official developer documentation. The listed trade endpoints
are Path of Exile website endpoints, not a PoEDB-hosted price service.

The linked page is also for the original PoEDB site. `poe2db.tw` does not currently expose the
same `/us/Developer_API` page.

## Verified source capabilities

| Need | Preferred source | What it supplies | Important limitation |
| --- | --- | --- | --- |
| Base items, classes, mods, tiers, tags, uniques, skills | RePoE PoE2 exports | Structured, patch-versioned JSON | Data-mined; some crafting target tables and exact probabilities are absent |
| Currency Exchange history | GGG public Currency Exchange API | Hourly markets, ratios, stock ranges, and traded volume | No current-hour data; old history may later be removed |
| Current item listings and explicit prices | Existing Path of Exile trade2 search/fetch | Individual listings and seller-entered prices | Unsupported website API; do not expand into bulk ingestion without approval |
| Trade-search base types and stat IDs | Path of Exile trade2 data endpoints | Base/unique names and searchable stat definitions | Patch metadata, not full game data |
| Unique-item aggregate prices | poe2scout | Current aggregate, quantity, and price logs | Third-party aggregate; not authoritative live transactions |
| Convenient exchange aggregates and seven-day curves | poe.ninja | Normalized prices, volume, and sparkline | Third-party supported economy surface, but unversioned and without an SLA |
| Small missing crafting tables | Targeted PoE2DB review | Human-readable mappings such as Alloy/Essence target tables | HTML is not a stable API contract |

## Existing static-data implementation

The repository already has the bulk static-data pipeline that a full PoE2DB crawl was intended to
provide:

- `npm run sync:poe2-data` discovers all root-level RePoE PoE2 `.min.json` exports;
- the current snapshot contains 24 sources, including 5,246 base items, 16,678 mods, and 449
  uniques;
- the sources are packed into a content-addressed gzip artifact;
- `manifest.json` pins the RePoE version, record counts, byte length, and SHA-256;
- readiness checks fail loudly on corruption or unexpected upstream changes;
- Coach already parses this snapshot and can map copied in-game item text to bases and modifiers.

The current manifest is documented in `src/data/poe2/README.md` and generated by
`src/scripts/syncPoe2GameData.ts`.

PoE2DB is currently used only as a reviewed cross-check for Alloy and Essence target mappings in
`services/coach/src/items/alloy.py` and `services/coach/src/items/essence.py`.

## Official Currency Exchange history

GGG now documents this public PoE2 endpoint:

```text
GET https://web.poecdn.com/api/currency-exchange/poe2/<hour-id>
```

Reference: [GGG API Reference — Currency Exchange](https://www.pathofexile.com/developer/docs/reference#currencyexchange)

The response is an hourly digest across leagues. Each market includes:

- `league`;
- `market_id` and `market_pair` using internal base-item IDs;
- `volume_traded` for both sides;
- `lowest_stock` and `highest_stock`;
- `lowest_ratio` and `highest_ratio`.

The response also returns `next_change_id`, a Unix timestamp truncated to the hour. GGG states
that when this value equals the requested value, the stream has reached its current end.

A read-only probe for `2026-08-06T10:00:00Z` returned:

- next cursor: `1786014000`;
- 1,962 market rows;
- five leagues, including `Runes of Aldur`;
- approximately 1.6 MB of JSON before compression.

The endpoint does **not** expose the current hour. GGG also warns that old history may be removed,
so useful digests should be persisted locally instead of repeatedly backfilled.

### Proposed local schema

```text
exchange_hour
  hour_id            integer primary key
  fetched_at         text
  payload_sha256     text

exchange_market_hour
  hour_id            integer
  league             text
  market_id          text
  left_item_id       text
  right_item_id      text
  left_volume        integer
  right_volume       integer
  left_stock_low     integer
  left_stock_high    integer
  right_stock_low    integer
  right_stock_high   integer
  left_ratio_low     integer
  left_ratio_high    integer
  right_ratio_low    integer
  right_ratio_high   integer
  primary key (hour_id, league, market_id)
```

Keep the raw compressed response or its hash alongside normalized rows. This makes parsing changes
auditable and allows a failed migration to be reproduced.

### Identifier mapping

The exchange response uses identifiers such as:

```text
Metadata/Items/Currency/CurrencyRerollRare
```

Map these IDs to display names and item metadata through the pinned RePoE `base_items` source.
Use trade2 item/static metadata only as a checked fallback. Do not maintain a hand-written name
map unless an upstream ID is genuinely missing.

### Ingestion behavior

1. Start after the previous completed hour.
2. Request one digest and parse the rate-limit response headers.
3. Validate the complete payload with a runtime schema before writing anything.
4. Filter to the configured league during normalization, but retain the raw digest for audit.
5. Insert the hour and all market rows in one transaction.
6. Persist `next_change_id` only after that transaction commits.
7. Stop when the returned cursor equals the requested cursor.
8. Poll again after the next hourly boundary with jitter and backoff.

The API documentation describes the `hour-id` as a timestamp received from the endpoint. A recent
timestamp worked in the probe, but bootstrap-from-arbitrary-timestamp behavior should be treated as
empirical until GGG confirms it. Do not make a production backfill depend silently on that detail.

## Can this replace poe.ninja?

### Yes, for part of the application

The official stream is a stronger source for historical Currency Exchange activity because it is
published by GGG and represents exchange activity rather than a third-party estimate. It can
eventually replace poe.ninja for:

- historical exchange ratios;
- hourly traded volume;
- exchange stock ranges;
- market-pair discovery;
- locally computed multi-day movement and liquidity scores.

### No, not as a universal replacement

It does not provide:

- the current incomplete hour;
- unique equipment prices;
- rare-item comparables;
- seller listings;
- finished normalized item names/icons;
- a ready-made seven-day sparkline;
- a complete static mod database.

For unique gear, keep poe2scout or calculate aggregates from compliant trade2 samples. For rare
gear, keep direct trade2 comparables. For static item/mod data, keep RePoE.

A safe migration is therefore **source-by-source**, not deleting `ninjaClient.ts` immediately.
Run both exchange pipelines in shadow mode first and compare normalized values for at least seven
days.

## Why not scrape all of PoE2DB?

`https://poe2db.tw/robots.txt` currently allows crawlers, but that is not a stable API contract or
a grant to republish the whole database.

The bulk-crawl approach has several problems:

- page structure and rendered tables can change without schema versioning;
- automated fetches have already produced 403/blank responses in previous research;
- crawling thousands of pages duplicates the structured RePoE snapshot we already have;
- partial failures can silently leave an internally inconsistent catalog;
- PoEDB labels wiki content as CC BY-NC-SA 3.0, which is unsuitable for casually embedding in a
  potentially commercial product without a licensing review;
- GGG prohibits reverse-engineering endpoints outside its documented resources;
- scraped prose and game data have different provenance and should not be mixed into one database.

If a PoE2DB-only table is required, implement a targeted importer with:

- an explicit allowlist of URLs;
- a descriptive, contactable user agent;
- low request rate and persistent cache;
- saved source URL, fetch time, parser version, and content hash;
- strict row-count/invariant checks;
- a fixture-based parser test;
- attribution and a licensing decision before redistribution.

Do not build a generic recursive crawler.

## Recommended migration plan

### Phase 1 — research spike

- Define a runtime schema for the GGG hourly response.
- Fetch one completed hour and map internal IDs through RePoE.
- Verify ratio direction using known Divine/Exalted/Chaos pairs.
- Measure compressed payload size and normalized row count for `Runes of Aldur`.
- Confirm applicable rate-limit headers and bootstrap behavior.

### Phase 2 — shadow ingestion

- Add the two local exchange-history tables.
- Ingest GGG data hourly without changing user-visible prices.
- Compare it against the existing poe.ninja snapshots for seven days.
- Report coverage, age, ratio divergence, and volume divergence.

### Phase 3 — controlled cutover

- Use GGG history for exchange trend/liquidity scoring.
- Keep poe.ninja as a separately labelled freshness/fallback source initially.
- Keep poe2scout for unique aggregates and trade2 for live comparables.
- Remove a third-party source only after coverage and failure behavior are proven in production.

### Phase 4 — targeted gap importers

- Inventory facts still missing from RePoE and the official API.
- Add a PoE2DB importer only for each concrete missing table.
- Never infer exact crafting probabilities when the upstream data lacks spawn weights.

## Compliance notes

- Follow [GGG's API policies and rate limits](https://www.pathofexile.com/developer/docs).
- The official docs provide no general PoE2 in-game data export beyond supported APIs and the
  passive tree. RePoE remains a community data-mining source, not an official GGG export.
- Public products must include GGG's required non-affiliation notice.
- Review PoEDB licensing and obtain permission before any bulk mirroring or commercial reuse.
- These notes are engineering guidance, not legal advice.
